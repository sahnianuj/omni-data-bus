# Upgrading from 1.0 to 2.0

2.0 upgrades in place: projects, repositories, mappings and job history are kept, and the API stays backward compatible under `/api/v1` (2.0 only adds fields and routes).

## Before you start

1. **Run 1.0.1 or later.** It adds two guards that make a rolling upgrade safe: its workers skip jobs that need 2.0 (`minWorkerVersion`), and its API refuses to edit a mapping saved by 2.0 (`409 MAPPING_NEWER_VERSION`) instead of dropping what it doesn't understand.
2. **Back up the metadata** (the Capella bucket's backup, or `cbbackupmgr` for self-managed Couchbase). Downgrading after 2.0 has saved mappings isn't supported; restoring the backup is the way back.

## What changes in the metadata

`odb admin migrate` (the Helm pre-upgrade hook) applies the new provisioning steps; it is idempotent and takes seconds whatever the data volume:

| Step | Adds |
|---|---|
| 4 | `relationships` collection (virtual relationships) |
| 5 | `exports` collection (export history) |
| 6 | `idx_jobs_claim` index (version-aware job claiming) |

Mappings are **not** rewritten: a 1.0 spec is upgraded when it's read and stored as v2 the next time it's saved. Jobs from 1.0 keep working; imported runs and new jobs carry `origin` and `minWorkerVersion`.

## Helm

```bash
helm upgrade odb oci://ghcr.io/sahnianuj/charts/omni-data-bus --version 2.0.0 -f values.yaml   # runs `odb admin migrate` first
```

New values (all optional):

```yaml
directoryTarget:          # directory targets (a volume at /data/odb-out in every pod)
  enabled: true
  persistence: { accessMode: ReadWriteMany, size: 50Gi }
exports:                  # what exported scripts run and download
  image: ""               # default: the image this chart deploys (pin by digest)
  downloadUrl: ""         # default: this version's GitHub release
worker:
  memoryLimitMB: 640      # OC_MEMORY_LIMIT_MB: Go soft memory limit, under resources.limits.memory (1Gi)
```

2.0 processes set a Go soft memory limit, `OC_MEMORY_LIMIT_MB` (default 640; `0` turns it off, and `GOMEMLIMIT` takes precedence). Large documents, such as hundreds of embedded rows each, allocate quickly. Without the limit, a worker's RSS went past 1 GB, beyond the chart's 1Gi pod limit. If you raise the pod's memory limit, raise this setting with it.

During the rollout 1.0.1 and 2.0 pods run side by side: 1.0.1 workers keep claiming jobs they can run, 2.0-only jobs (directory targets, relations, composed documents, grouping, aggregates) wait for 2.0 workers, and the UI stays available.

## Docker Compose / all-in-one image

Pull the new image and restart: `docker compose pull && docker compose up -d` (the server migrates the metadata on start when `OC_META_AUTO_PROVISION` is on, the default), or `./run.sh load` and `./run.sh start` for the all-in-one image.

## Rolling back

Before any 2.0-only feature is used, 1.0.1 still runs against the upgraded metadata (it ignores the new collections). After mappings were saved by 2.0, restore the backup taken before the upgrade.
