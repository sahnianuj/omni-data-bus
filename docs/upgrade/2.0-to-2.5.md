# Upgrading from 2.0 to 2.5: exports and the odb runner

This page covers what changes for **exported migrations** in 2.5 (OC-180 to OC-186). The server upgrades in place as in 2.0. The 2.5 [release notes](../release-2.5.0/RELEASE-NOTES.md) list everything else.

## 2.5 exports have no `migrate.sh`

An export is now `config.json`, `mappings.json` and `README.md`. Install odb 2.5 on the machine, then run the export in its folder:

```
odb preflight
odb run
```

The commands are the same on macOS, Windows and Linux. The README links each machine's odb download, with its checksum. For a machine without internet access, export with **Add odb for a machine without internet access**: the folder then holds `bin/odb` (`bin/odb.exe` on Windows).

| 2.0 (`migrate.sh`) | 2.5 (`odb`) |
|---|---|
| `./migrate.sh preflight` | `odb preflight` |
| `./migrate.sh run -- --throttle 5000` | `odb run --throttle 5000` |
| `./migrate.sh resume` / `status` / `verify` / `inspect` | `odb resume` / `status` / `verify` / `inspect` |
| `ODB_CONFIG`, `ODB_MAPPINGS`, `ODB_STATE_DIR`, `ODB_TARGET_PATH` | the same variables, or `--config`, `--mappings`, `--state-dir`, `--target-path` |
| `ODB_RUNTIME=docker`, `ODB_DOCKER_ARGS` | the README's `docker run … <image> preflight` command |
| `ODB_BIN`, `ODB_CACHE_DIR` (find or download odb) | install odb once; nothing is downloaded at run time |

## 2.0 exports keep working

- **`./migrate.sh run` still works.** A 2.0 export's script runs odb of its own release (2.0), as before: it only accepts that version, and finds or downloads it itself.
- **odb 2.5 also runs a 2.0 export folder directly.** Run `odb preflight` and `odb run` in it: odb finds the folder's `config.json` and `mappings.json`, and a 2.0 export accepts any odb from 2.0 up to, but not including, 3.0.
- **On a terminal, odb 2.5 prints progress as text.** Piped or in a container, it's still JSON lines, and `--log-format json` forces JSON.

## For automation

- **Exit codes** are unchanged: 0, 2, 3, 4, 5.
- **Output**: JSON events on stdout whenever stdout isn't a terminal. The `start` event adds `mappingsFile` and `configFile`.
- **Export API**: `POST /projects/{id}/exports` without `includeOdb` now returns the folder with no binary. `includeOdb` accepts `windows` and `universal` (one macOS binary). `GET /exports/options` adds `signed` and drops `autoEmbed`.

## For the server

- **Any machine's odb in an export (OC-188)**: nothing to set up when the server can reach the release. The first export for a machine downloads its odb from `OC_EXPORT_DOWNLOAD_URL` (this version's GitHub release by default), checks it against the checksums built into the image, and caches it in `OC_EXPORT_CACHE_DIR`. Helm mounts a 256 MiB cache volume (`exports.cacheSize`). If the repository's releases aren't public, point `OC_EXPORT_DOWNLOAD_URL` at a mirror the server can reach.
- **A server without internet access**: set `OC_EXPORT_FETCH=false` (Helm `exports.fetch: false`). Put a 2.5 release's odb archives (the `.tar.gz` files, the Windows `.zip` files, `SHA256SUMS` and `SIGNED`) in `OC_EXPORT_DIST_DIR` (Helm `exports.distDir.existingClaim`, a PVC holding them). The export dialog says, for each machine, whether its odb is available, downloaded on first use, or why not.
- **Self-built binaries**: a dist built with `make dist` has no `SIGNED` file. Its macOS and Windows binaries are reported as unsigned, and the dialog and README say so.
